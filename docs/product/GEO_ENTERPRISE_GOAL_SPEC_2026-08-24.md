## 1. 这次 Goal 到底要解决什么

一句话目标：

> 把当前“能看数据、能生成内容”的 GEO 工作台，升级为企业真正能分工执行、持续观测、验证效果并核算回报的经营系统，同时用平台自己的“GEO 文章助手”完成安全、可审计的多平台草稿交付。

企业最终需要回答六个简单问题：

1. 现在最值得做什么？
2. 这件事应该走哪条执行流程？
3. 谁负责，什么时候必须完成，现在卡在哪里？
4. 完成后，哪些问题和模型可以立即复测？
5. GEO 指标和业务结果到底有没有变好？
6. 如果突然变差，系统能不能主动告诉我？

如果某项开发不能更可靠地回答以上问题，就不进入本次 Goal。

## 2. 第一性原理与删减结论

### 2.1 产品的最小真实闭环

GEO 服务不是“生成文章”，而是以下闭环：

`统一观测范围 → 发现问题 → 建立行动 → 真实执行并留证 → 只复测受影响范围 → 对比变化 → 连接业务结果 → 决定继续、调整或停止`

因此，系统的三块公共底座必须先统一：

- **统一范围**：时间、批次、模型、问题必须是同一个口径。
- **行动账本**：行动类型、负责人、期限、审批、阻塞和证据必须可追溯。
- **证据账本**：草稿、上线、发布、复测、线索和成交必须区分真实状态，不能靠文案推断完成。

### 2.2 对七项要求的判断

| 要求 | 是否做 | 第一性原理判断 | 最小可靠实现 |
| --- | --- | --- | --- |
| 优化行动按类型分流 | 做，P0 | 不同结果物、负责人和完成证据完全不同 | 先定义 4 类行动及 4 条状态机 |
| 单目标完成即可复测 | 做，P0 | 复测应验证一个已发生的干预，不应被无关目标拖住 | 基于完成目标的影响范围创建局部复测 |
| 负责人、截止时间、审批期限 | 做，P0 | 企业执行没有责任和时限就无法管理 | 单负责人、截止时间、审批 SLA、阻塞原因 |
| 全站统一数据范围 | 做，P0，先做底座 | 页面口径不一致会让所有结论失真 | 一个全局范围对象，页面只消费它 |
| 定时观测和变化告警 | 做，P0 | 企业不能依赖人工每天巡检 | 计划任务、确定性规则、站内通知、去重冷却 |
| ROI CSV 批量导入 | 做，P0 | 逐条手填无法形成长期数据 | 模板、预检、映射、幂等导入、错误报告 |
| GEO 文章助手 | 做，P0，但有许可与安全门禁 | 平台需要控制自己的交付闭环，但不能盲拷贝高权限代码 | 平台原生 UI + 独立浏览器扩展 + 精简平台适配器 |

### 2.3 明确不做

本次 Goal 不做以下内容：

- 不自动点击目标平台的最终“发布”按钮。
- 不把草稿链接返回、同步请求成功、Agent 任务完成当成真实发布或 GEO 改善。
- 不同时接 CRM；先证明 CSV 批量导入能稳定使用。
- 不为 29 个平台一次性做全适配；先覆盖当前 GEO 业务真正使用的平台。
- 不复制上游扩展的品牌、广告、文章抓取器、独立内容后台、CLI、MCP 远程桥接等无关能力。
- 不把 Cookie、密码、会话、平台 Token 上传到 GEO API。
- 不为了收敛导航删除旧路由、历史数据或可回读证据。
- 不在没有 image2 设计稿和设计自审记录时直接写新功能界面。

## 5. 公共底座一：全站统一数据范围

### 5.1 用户看到什么

所有经营与分析页面顶部共用一条“范围栏”：

- 时间：最近 7/30/90 天或自定义
- 观测批次：默认最近完整批次，可多选历史批次
- 模型：多选，使用官方 Logo
- 问题：多选，可按问题组快速选择
- 当前范围摘要：例如“近 30 天 · 3 个批次 · 4 个模型 · 12 个问题”

用户切换页面时范围不丢失；主动点击“重置”才恢复默认值。

### 5.2 系统怎么保证口径一致

建立唯一 `GlobalScope`：

- `workspace_id`
- `date_from` / `date_to`
- `batch_ids[]`
- `model_keys[]`
- `question_plan_ids[]`
- `scope_version`
- `scope_fingerprint`
- `updated_by_user_id`
- `updated_at`

原则：

- 所有页面和 API 接受同一种范围结构，不再各自发明筛选参数。
- “最近 30 天”和“批次 93”不是同一概念；系统要显示两者如何共同限制数据。
- 用于复测的基线范围一旦建立即冻结，后续全局范围变化不能偷偷改写历史行动。
- 不支持某个维度的页面必须明确显示“此页不受批次筛选影响”，不能静默忽略。
- URL 保存可分享的范围标识；刷新、后退和深链接行为一致。

### 5.3 验收

- 在洞察选择多个模型和问题，进入行动、内容、效果页后范围保持一致。
- 每个图表、表格和结论能回读它实际使用的范围指纹。
- 相同范围在不同页面的样本数能够解释，不能出现无来源的数字差异。
- 历史复测仍使用创建时冻结范围，不被全局筛选覆盖。

## 6. 公共底座二：优化行动按类型分流

### 6.1 四类 P0 行动

#### A. 发布文章

流程：`确定问题 → 生成平台差异稿 → 事实审核 → 平台稿审批 → GEO 文章助手写入草稿 → 用户人工发布 → 公网核验 → 局部复测`

真实完成证据：

- 与行动目标匹配的公开文章 URL；
- 公网可访问；
- 页面标题和正文关键指纹可回读；
- 平台、账号、发布时间和内容版本可追溯。

#### B. 修改官网

流程：`确定页面与缺口 → 生成修改建议/草稿 → 品牌和法务审核 → 交给网站负责人 → 上线 → 同域页面回读 → 局部复测`

真实完成证据：

- 指定官网 URL 公网可访问；
- 目标标题、段落、链接或声明确实出现在页面；
- 对应上线版本、负责人和时间可追溯。

官网行动不进入文章分发流程。

#### C. 补结构化数据

流程：`识别页面与 Schema 缺口 → 生成 JSON-LD 建议 → 技术审核 → 部署 → 抓取页面源码 → 结构校验 → 局部复测`

真实完成证据：

- 指定页面中出现目标结构化数据；
- JSON 可解析，类型和必填字段符合规则；
- 部署前后代码指纹和验证结果可追溯。

结构化数据行动不生成平台文章。

#### D. 建设第三方信源

流程：`选择目标信源 → 明确合作/编辑任务 → 负责人执行 → 外部内容上线 → 公网回读品牌与关键事实 → 局部复测`

真实完成证据：

- 第三方公开 URL；
- 页面确实包含目标品牌、实体或关键事实；
- 信源域名、内容类型、发布时间和关系可追溯。

第三方信源行动不能伪装成我们自己发布的文章。

### 6.2 数据结构

行动新增或明确以下字段：

- `action_type`：`article` / `official_site` / `structured_data` / `third_party_source`
- `deliverable_type`
- `target_refs[]`：目标平台、页面或信源
- `affected_question_ids[]`
- `affected_model_keys[]`
- `assignee_user_id`
- `due_at`
- `approval_due_at`
- `approval_requested_at`
- `blocked_reason_code`
- `blocked_note`
- `completion_evidence_ids[]`
- `completed_target_count`
- `retest_eligible_target_count`

旧行动必须通过可解释迁移规则映射；无法判断的旧数据标记为 `legacy_unclassified`，不能默认归为文章。

### 6.3 状态不能共用一条流水线

所有行动共享“提出、负责、审批、阻塞、完成、复测”这些企业状态，但每类行动拥有自己的交付状态。

共享状态：

`proposed → accepted → in_progress → awaiting_approval → executing → partially_completed → completed → retesting → measured`

同时保留：

- `blocked`
- `cancelled`
- `changes_requested`
- `retest_inconclusive`

“部分完成”必须是有真实目标证据，不是进度条估算。

### 6.4 验收

- 新建四类行动时，只出现与该类型相关的步骤和字段。
- 官网与结构化数据行动绝不出现“生成平台稿—文章同步助手”。
- 旧数据可回读且不丢失历史事件。
- 非法跨阶段转换被后端拒绝并记录审计事件。

## 7. 公共底座三：负责人、截止时间和审批期限

### 7.1 最小企业规则

- 每个进入 `accepted` 的行动必须有一个直接负责人。
- 每个行动必须有交付截止时间。
- 进入 `awaiting_approval` 时必须生成审批截止时间。
- 负责人可以移交，但必须保留移交记录。
- “卡住”必须选择标准原因并补充说明，不能只显示“处理中”。

### 7.2 用户界面

行动卡片直接显示：

- 负责人头像和姓名
- 截止日期
- 当前停留时长
- 审批剩余时间或逾期时长
- 阻塞原因
- 下一步唯一主操作

行动页增加三个企业视图：

- 我的行动
- 待我审批
- 已逾期/被阻塞

### 7.3 通知规则

- 截止前 24 小时提醒负责人。
- 审批剩余 8 小时提醒审批人。
- 到期未处理变为逾期并通知负责人和工作区管理员。
- 相同事件只提醒一次；状态变化后再产生新提醒。

P0 先做站内通知；邮件、飞书或企业微信作为后续通知渠道，不阻塞本次 Goal。

### 7.4 验收

- 无负责人或截止时间的行动不能进入执行状态。
- 审批倒计时基于服务端时间，可被数据库回读。
- 转交、延期、退回和逾期都有不可变审计事件。
- 权限不足的用户不能替别人审批或改负责人。

## 8. 修改复测开放逻辑

### 8.1 新规则

旧规则“所有平台全部发布后才能复测”必须删除。

新规则：

> 任意一个行动目标真实完成、证据通过验证，并且它明确关联了受影响的问题和模型，就可以只对该目标的影响范围创建复测。

### 8.2 范围如何计算

一次局部复测由以下内容冻结：

- 完成目标 ID
- 完成证据 ID 与证据哈希
- 受影响问题 ID 集合
- 受影响模型集合
- 基线批次与基线样本数
- 重复次数
- 创建复测时的范围指纹

多个目标可以分别复测，也可以在口径完全一致时合并。系统不能为了省任务把不同问题、不同模型或不同基线硬合并。

### 8.3 状态解释

- `eligible`：已有一个目标真实完成，可以复测。
- `partially_measured`：部分完成目标已有复测结果，其他目标仍在执行。
- `measured`：所有要求测量的完成目标都已有有效结果。
- `inconclusive`：样本不足、范围不一致或模型异常，不能得出行动有效性结论。

### 8.4 验收

- 一个四平台行动中，知乎先真实发布并验证后，可以立即复测知乎所影响的问题/模型。
- 未完成平台不进入该轮复测归因，也不阻塞已完成平台。
- 复测结果清楚显示“这轮测了哪个完成目标”，不能看起来像整项行动全部完成。
- 草稿保存、候选链接或人工填写但未公网验证的 URL 均不能解锁复测。

## 9. 定时观测与变化告警

### 9.1 先解决的用户问题

用户不应该每天打开所有页面寻找异常。系统应主动告诉他：

- 品牌可见度明显下降；
- 竞品可见度明显上升或超过品牌；
- 重要信源新增、消失或权重显著变化；
- 某个模型连续失败、响应口径异常或样本不完整。

### 9.2 P0 能力

#### 定时观测

- 支持每日、每周和自定义工作日。
- 每个计划明确问题、模型、重复次数和时区。
- 使用固定范围快照和版本号，后续修改不改写历史任务。
- 跳过重复排队；同一计划同一时间窗只能有一个有效任务。

#### 变化检测

先使用可解释的确定性规则，不把 AI 文案当告警判断：

- 品牌可见度较基线下降超过阈值，且样本完整；
- 竞品可见度上升超过阈值或排名反超；
- 核心信源权重跨档、引用次数突降或首次出现；
- 模型失败率、超时率或空答率超过阈值；
- 关键问题从“出现品牌”变为“未出现品牌”。

#### 告警卡片

每条告警必须包含：

- 发生了什么；
- 与哪个基线相比；
- 涉及哪些问题、模型或信源；
- 样本是否完整；
- 原始证据入口；
- 建议动作；
- 确认、忽略、转成行动。

### 9.3 防止告警轰炸

- 相同范围、相同原因在冷却期内合并。
- 数据不完整时显示“观测异常”，不能误报“品牌下降”。
- 告警关闭后，只有出现新的有效批次或跨越更高阈值才重新打开。
- P0 默认站内通知；外部通知连接器后置。

### 9.4 验收

- 真实调度能生成有数据库记录的观测批次，不是前端假状态。
- 人工构造的下降、竞品反超、信源变化和模型失败均触发正确告警。
- 重复运行不重复轰炸。
- 每条告警可以从证据追到批次，也可以一键建立带范围的优化行动。

## 10. ROI 第一阶段：CSV 批量导入

### 10.1 产品定位

ROI 页只做一个工具：

> 把企业已有的成本、AI 引荐访问、线索、商机和成交记录批量放进系统，并按行动与时间范围直观看到投入、产出和 ROI。

不教育用户，不用大段文案代替数字，不在证据不足时硬算 ROI。

### 10.2 CSV 标准模板

| 字段 | 必填条件 | 说明 |
| --- | --- | --- |
| `record_id` | 必填 | 企业侧唯一 ID，用于去重 |
| `occurred_at` | 必填 | 发生时间，带时区或按工作区时区解析 |
| `metric_type` | 必填 | 成本、访问、线索、商机、商机金额、成交收入 |
| `amount` | 金额类必填 | 原始金额，不使用浮点累计 |
| `quantity` | 数量类必填 | 访问、线索或商机数量 |
| `currency` | 金额类必填 | CNY、USD 等 ISO 货币码 |
| `action_id` | 直接归因必填 | 关联优化行动 |
| `attribution_type` | 必填 | direct / assisted / unallocated / not_applicable |
| `source_type` | 必填 | analytics / crm / finance / manual_import |
| `source_reference` | 直接成交必填 | CRM、财务或业务凭证编号 |
| `source_label` | 必填 | 文件或系统名称 |
| `evidence_note` | 必填 | 这条记录代表什么 |

### 10.3 导入流程

`下载模板 → 上传 CSV → 自动识别列 → 用户确认映射 → 数据预检 → 显示可导入/需修复/重复 → 用户确认 → 后端幂等写入 → 返回导入报告`

预检必须发现：

- 缺列、格式错误、非法币种；
- 行动不存在或不属于当前工作区；
- 直接成交缺少行动或凭证；
- 金额和数量同时填写；
- 重复 `record_id`；
- 文件内重复行；
- 时间超出合理范围；
- 可能的公式注入内容。

### 10.4 数据规则

- 先预检，确认后才入库。
- 导入以 `import_batch_id + record_id` 幂等；重复提交不重复记账。
- 成功与失败行分开报告；失败行可下载修正。
- 已确认记录不直接修改，使用冲销记录保留审计链。
- 多币种分别展示；没有汇率来源时不强行合并 ROI。
- 只有有行动、有 CRM/财务凭证的直接成交进入直接 ROI。
- 辅助收入、商机金额和线索单独展示，不混入直接 ROI。

### 10.5 ROI 页面最小结构

- 顶部：时间、行动多选、币种。
- 核心数字：投入、直接成交、净收益、ROI。
- 辅助数字：AI 引荐访问、有效线索、商机、辅助收入。
- 趋势：投入与直接成交的时间趋势。
- 行动表：每项行动的投入、GEO 效果、访问/线索、成交、ROI。
- 数据入口：导入 CSV、查看导入记录、下载错误报告。

### 10.6 验收

- 标准模板可下载，真实 CSV 可批量导入。
- 同一文件重复导入不会重复计数。
- 错误行有精确到行和字段的原因。
- 冲销后总额、趋势和行动明细一致。
- 多币种或缺少凭证时明确显示不可计算，不用 0 冒充。
- 导入后的数据能与当前行动和全局范围联动。

## 11. GEO 文章助手：从外部依赖变成平台原生能力

### 11.1 “原生”是什么意思

原生不是假装浏览器跨站限制不存在。它意味着：

- 用户只在春秋元泉 GEO 中选择内容、账号和平台；
- 状态、审批、失败、重试和证据都回到 GEO 行动账本；
- 不再要求用户填写第三方 MCP 路径和 Token；
- 浏览器扩展只是受控执行层，不再拥有一套独立产品流程；
- 平台 Cookie 留在浏览器中，不进入 GEO 后端。

产品名称统一为 **GEO 文章助手**。

### 11.2 上游事实和许可门禁

参考上游为 [wechatsync/Wechatsync](https://github.com/wechatsync/Wechatsync)。当前公开仓库说明其为 Manifest V3 浏览器扩展，支持草稿模式和多平台适配，并采用 **GPL-3.0**。上游扩展当前还申请了 `cookies`、`scripting`、`tabs`、`downloads` 以及 `http://*/*`、`https://*/*` 等广泛权限。

因此“基本一比一复刻”只能理解为复用已验证的交互思路和需要的业务能力，不能直接解释为：

- 去掉上游名称后整包复制；
- 忽略 GPL-3.0 的源码、许可证和修改声明义务；
- 原样保留全站高权限；
- 把上游的自动/批量发布能力带入本产品。

正式编码前必须选择并记录一条路径：

#### 推荐路径 A：独立 GPL 扩展

- `GEO 文章助手` 作为与主平台边界清楚的独立扩展组件。
- 如果复用或修改上游代码，该扩展按 GPL-3.0 保留许可证、版权和修改说明，并提供对应源代码。
- 主平台通过版本化消息协议与扩展通信，不把 GPL 代码直接混入主平台业务模块。
- 发布或向客户交付前由负责人复核许可证履行方式。

#### 备选路径 B：全新 clean-room 实现

- 只依据公开行为、平台接口和我们自己的协议重新实现。
- 不复制上游受版权保护的源代码、素材、品牌和内部结构。
- 仍需要单独完成平台条款、安全和商标审查。

如果企业不接受路径 A 的开源义务，又没有资源完成路径 B，本工作流必须暂停并重新决策，不能偷偷继续复制。

### 11.3 第一性原理保留的能力

P0 只保留：

- 检测当前浏览器已登录的目标平台账号；
- 显示官方平台 Logo 与明确账号；
- 接收已审核、带版本哈希的平台差异稿；
- 转换并保持基本标题、正文、链接、图片和代码块格式；
- 按平台顺序写入草稿；
- 返回候选草稿地址和外部草稿 ID；
- 打开草稿供用户确认；
- 按平台保存成功、失败和重试结果；
- 不重复创建已成功草稿；
- 显示插件版本、权限、连接和平台登录健康。

P0 平台：

- 知乎
- 掘金
- CSDN
- 51CTO
- 微信公众号

添加其他平台必须有真实企业使用需求和独立验收，不因为上游支持 29+ 平台就全部搬入。

### 11.4 删除的能力

- 从任意网页提取文章；
- 单独的文章创作器和独立内容库；
- CLI、Claude MCP、远程 WebSocket 桥接；
- 自动发布或批量最终发布；
- 与 GEO 无关的平台和下载工具；
- 广告、统计、推荐、上游品牌入口；
- 全站悬浮按钮、右键菜单和不必要的下载权限；
- 把平台 Cookie、Token 或密码传给 GEO API 的任何路径。

### 11.5 最小架构

#### GEO 平台

- 创建一次性同步任务；
- 任务只允许引用“已审核内容版本”；
- 保存任务、平台目标、内容哈希、操作者和审计事件；
- 接收逐平台候选草稿结果；
- 继续保留人工最终发布门禁。

#### GEO 文章助手扩展

- Manifest V3；
- 只申请 P0 平台与 GEO 平台域名所需的最小权限；
- 登录态只在本机浏览器使用；
- 平台适配器统一实现：`detectAccount`、`writeDraft`、`readBackDraft`、`openDraft`；
- 平台逐个执行，单个平台失败不覆盖已成功结果；
- 不提供最终发布方法。

#### 通信协议

- 只接受允许来源的消息；
- 使用一次性 nonce、短期任务令牌、协议版本和任务过期时间；
- 每个任务绑定工作区、行动、内容版本、目标平台和操作者；
- 消息只携带必要业务内容，不携带平台 Cookie 或 GEO 密钥；
- 后端校验内容哈希、目标平台和幂等键后才保存结果。

### 11.6 原生交互

在内容页或行动页点击“写入平台草稿”，打开平台内的 GEO 文章助手面板：

1. **内容确认**：标题、内容版本、通过审批的人和时间。
2. **平台与账号**：官方 Logo、账号名称、登录状态、多选。
3. **写入草稿**：逐平台真实状态，不显示虚构百分比。
4. **结果确认**：成功目标可打开草稿；失败目标可以单独重试。
5. **发布回执**：用户在平台最终发布后，把公开 URL 交回系统核验。

没有安装扩展时，产品显示自己的安装引导；不再出现第三方“文章同步助手”品牌或 MCP 配置表单。

### 11.7 安全和隐私验收

- 扩展权限清单逐项有业务理由，没有 `<all_urls>` 式默认全站权限。
- Cookie、密码、浏览器会话和平台 Token 不进入 API、数据库、日志、工件或 Git。
- 不接受其他网页伪造的同步消息。
- 内容版本变化后，旧审批和旧同步任务自动失效。
- 重复点击、超时重试和浏览器恢复不会创建不可控重复草稿。
- 所有平台适配器均验证“只保存草稿、不发布”。
- 至少两个 P0 平台先完成真实草稿闭环，随后按同一验收标准扩展到其余平台。

## 12. Apple Design 与 image2 强制设计门禁

每个新功能必须遵循：

`功能简报 → image2 设计图 → 内部设计自审 → 用户确认主要方向 → 从通过的设计图开发 → 真实浏览器验收`

### 12.1 哪些内容必须先出图

- 6 个一级导航和二级导航；
- 全局范围栏及多选展开态；
- 四类行动的看板与详情状态；
- 负责人、期限、审批和阻塞状态；
- 告警中心及告警展开态；
- ROI CSV 上传、字段映射、错误预检和导入完成态；
- GEO 文章助手未安装、账号选择、写入中、部分失败、成功确认态；
- 桌面端和关键移动端布局。

同一流程可以用一张多状态设计稿表达，不用为一个文字修正重复出图；但任何新的页面、核心组件或关键状态都不能跳过。

### 12.2 内部自审清单

设计图只有满足以下要求才算内部通过：

- 一眼看得出当前范围、主任务、状态和下一步；
- 主操作唯一，危险操作不抢视觉注意力；
- 使用系统字体、真实官方 Logo、克制的蓝色和中性色；
- 玻璃拟态只用于有层级意义的浮层或面板，不层层叠玻璃；
- 文字和边界对比度在浅色背景中足够清楚，不能用“浅灰代表高级”；
- 点击目标至少 44×44；键盘、焦点、读屏标签完整；
- 交互在 pointer-down 有即时反馈，动效可打断；
- 支持减少动态效果、增加对比度和减少透明度；
- 加载、空数据、部分成功、错误、逾期、无权限均有真实状态；
- 无假数据误导；用于视觉说明的示例数据必须明确是示例。

### 12.3 开发约束

- 实现必须对照已通过设计稿，不允许边写代码边随意改视觉方向。
- 如果数据或权限现实与设计图冲突，先回到设计图修订并重新审核。
- 视觉接近不等于完成；必须验收真实点击、滚动、筛选、返回、键盘和小屏状态。

## 13. 推荐开发顺序

### Phase 0：Goal 控制面与基线

- 确认本规格和 P0 边界；
- 初始化唯一 change bundle；
- 把每条需求、风险、影响文件和验收命令写入控制包；
- 再次验证回滚点和当前运行态。

停止点：规格无 `TODO_REQUIRED`，影响图完整，用户同意进入开发。

### Phase 1：统一范围与 6 入口信息架构

- 先生成 image2 设计稿并自审；
- 实现全局范围对象、范围栏、URL 与页面传递；
- 收敛导航但保留旧路由。

原因：后续所有功能都依赖统一口径。

### Phase 2：行动分流、责任与局部复测

- 为四类行动生成 image2 全状态设计；
- 新数据模型与可逆迁移；
- 四类状态机；
- 负责人、截止与审批 SLA；
- 任意完成目标触发局部复测。

原因：告警、内容、ROI 都必须落到可追溯行动。

### Phase 3：定时观测与变化告警

- image2 告警中心；
- 调度、范围快照、变化规则、去重与站内通知；
- 从告警直接建立行动。

### Phase 4：ROI CSV 批量导入

- image2 上传、映射、预检、结果态；
- CSV 模板、预检、幂等导入、错误文件与冲销；
- ROI 与行动/范围联动。

### Phase 5：GEO 文章助手

- 先作 GPL 路径与安全权限决策；
- image2 原生面板和插件健康页；
- 建立版本化通信协议；
- 先完成两个平台真实草稿闭环；
- 再扩展到剩余 P0 平台；
- 删除旧第三方 MCP 配置和外部品牌入口，但保留迁移期只读诊断与数据兼容。

### Phase 6：统一验收与收尾

- 独立 Checker 审查；
- 完整产品验收门；
- 用户浏览器验收；
- 记录明确人工签字；
- 才能结束 Goal。

每个 Phase 必须“实现 → 验证 → 再进入下一阶段”，不能一次改完后才发现范围和状态机都不一致。

## 14. 数据迁移与兼容原则

- 所有新表和字段使用版本化迁移，升级前自动创建数据库安全备份。
- 迁移不能删除现有行动、草稿、证据、复测或 ROI 记录。
- 旧同步助手记录继续可读；新任务只走 GEO 文章助手。
- 旧导航 URL 保留重定向，旧深链接可以打开对应二级页。
- 旧行动无法准确分类时保留 `legacy_unclassified`，由用户确认，不由脚本猜测。
- 所有写入接口有工作区权限、幂等键和审计事件。
- 所有完成状态都有数据库记录与可回读证据。
- 数据库降级路径必须在隔离副本验证；不在真实库上实验。

## 15. Goal 模式的完成条件

只有以下条件全部满足，才可以把 Goal 标记为完成：

### 15.1 需求完成

- 6 个一级入口在桌面和移动端可用，旧路由兼容。
- 全局范围在洞察、行动、内容、效果与 ROI 间一致传递。
- 四类行动各走正确流程。
- 负责人、截止时间、审批期限、阻塞和审计可用。
- 任一真实完成目标可以创建范围正确的局部复测。
- 定时观测能真实排队、完成并产生可解释告警。
- ROI CSV 可以预检、幂等导入、报告错误、冲销和联动计算。
- GEO 文章助手替代当前外部连接体验，完成 P0 平台目标；至少两个平台先有真实草稿闭环证据，其余平台逐一达到相同标准。

### 15.2 设计完成

- 每个新功能有 image2 设计稿和内部自审记录。
- 实现与通过的设计稿在结构、层级、主要状态和交互上一致。
- 用户已在真实浏览器确认关键页面，不只看静态截图。
- Apple Design 的动效、可访问性、透明度降级和对比度要求通过。

### 15.3 技术完成

- 当前 revision 与验收报告记录的 subject 完全一致。
- 数据迁移在隔离副本完成升级、回读和必要的降级验证。
- `pnpm run check:web` 通过。
- 受影响 API 检查通过。
- 从 `apps/api` 使用 `PYTHONPATH=.` 运行受影响测试通过。
- `git diff --check` 通过。
- 真实浏览器验收通过。
- 隐私文件审计通过。
- 扩展构建、加载、权限、消息防伪和平台适配测试通过。
- 没有高严重度未解决缺陷或阻塞。

### 15.4 业务真实性完成

- 不把测试数据、设计示例或历史数据说成新产生的业务效果。
- 复测结果能回到真实行动目标和证据。
- ROI 只使用符合归因边界的数据。
- GEO 文章助手没有触发最终发布；真实发布仍由用户在目标平台确认。
- 每个“已完成”都有数据库记录和回读证据。

### 15.5 独立验收与人工签字

- Maker 不能自己把实现说明当 Checker 结论。
- 高风险变更需要独立 Checker。
- 产品验收门对当前代码/扩展版本给出 `pass` 或经过用户同意的 `pass_with_concerns`。
- 用户明确说“通过/验收完成”后，才能记录人工签字。
- 未获得人工签字，技术工作即使全部通过也不能宣称 Goal 完成。

## 16. Goal 必须暂停或重新规划的停止条件

遇到以下任一情况，停止继续扩张代码，保存证据并汇报：

1. **许可冲突**：无法确认 GPL-3.0 路径，或企业既不接受开源扩展又不批准 clean-room 实现。
2. **安全越界**：实现需要把 Cookie、密码、会话或平台 Token 发送到 GEO 后端。
3. **发布越界**：平台适配器无法保证只写草稿，可能触发最终发布。
4. **数据风险**：迁移无法证明不会丢失现有数据，或回滚点验证失败。
5. **范围扩大**：开发中新增了本规格之外的 CRM、外部消息渠道或大量新平台。
6. **设计不成立**：image2 设计在真实数据、权限或小屏下无法成立，需要先改设计。
7. **运行态矛盾**：测试通过但真实 Web/API/扩展行为不一致。
8. **验收证据过期**：代码、数据库迁移、扩展或上游平台版本变化后仍试图复用旧报告。
9. **平台阻断**：验证码、平台风控或 DOM/API 变化使适配器无法稳定保存草稿。
10. **同一阻塞连续三轮**：在 Goal 模式连续三次仍是同一个外部阻塞且无法继续产生有效进展时，按规则标记 blocked 并等待用户或外部状态变化。
11. **用户改变目标**：用户提出会实质改变架构、许可或 P0 范围的新要求。
12. **回归出现**：旧行动、内容、复测、证据或登录流程被破坏。

暂停不等于失败。正确做法是保留当前迭代、影响、错误和验证证据，说明需要用户决定的具体事项，而不是用假完成绕过。

---

## 17. 哪些情况绝对不算完成

- 只有 image2 设计图，没有真实实现。
- 只有前端页面，没有数据库或 API 记录。
- 只有接口 200，没有真实业务回读。
- 只有构建通过，没有浏览器验收。
- 只有扩展显示“连接成功”，没有真实草稿链接和内容回读。
- 草稿已保存，但被说成公开发布。
- 一个目标完成，却被说成整项多目标行动完成。
- 一轮复测样本不完整，却给出“优化有效”的结论。
- ROI 缺少成本、行动或成交凭证，却显示 0% 或正收益。
- Agent 自己说通过，但独立 Checker、产品验收门或用户尚未确认。

## 18. Goal 启动时的执行协议

用户明确要求开始 Goal 后，执行顺序如下：

1. 重新核验仓库、分支、HEAD、进程 cwd、端口和数据库。
2. 确认本回滚点仍可读并创建当日二次安全检查。
3. 初始化唯一变更控制包，不并行创建第二套规格系统。
4. 把本文件每个 P0 需求拆成有稳定 ID 的验收条目。
5. 先做 Phase 1 的 image2 设计与自审，不直接修改功能代码。
6. 用户确认主要方向后，按 Phase 逐段实现和验证。
7. 每轮记录 Maker 产出、证据、Checker 结论和剩余阻塞。
8. 任何验收报告只绑定当时的精确 revision；变更后重新验收。
9. 达到第 15 节所有条件后请求用户最终验收。
10. 只有用户明确接受后，记录人工签字并结束 Goal。

## 19. 开发期间的固定汇报格式

每次阶段汇报只回答五件事：

1. 这一阶段解决了哪个真实业务问题？
2. 改了哪些可见能力和数据规则？
3. 哪些证据证明它真实可用？
4. 还有什么风险、阻塞或没有完成？
5. 下一阶段是什么，是否触发新的 image2 设计门禁？

禁止用“基本完成”“应该没问题”“看起来正常”代替证据。

## 20. 最终验收清单

用户验收时应能亲手完成以下路径：

1. 设置一个全局范围，在洞察、行动和效果页看到相同口径。
2. 分别打开文章、官网、结构化数据和第三方信源行动，看到完全不同的正确流程。
3. 给行动分配负责人、截止时间，提交审批并看到 SLA。
4. 只完成一个目标并留证，立即对它的影响问题和模型发起复测。
5. 建立定时观测，并看到一次真实变化告警及其证据。
6. 上传一份含正确、错误和重复行的 CSV，完成预检、导入和错误下载。
7. 在 ROI 中按多个行动查看投入、直接成交、辅助结果和不可计算边界。
8. 在平台内打开 GEO 文章助手，选择已登录账号，把已审核稿写入真实平台草稿。
9. 验证失败平台可以单独重试，成功平台不会重复创建。
10. 确认系统没有代替用户点击最终发布，也没有泄露平台登录凭据。

完成这十条仍需结合自动检查、独立 Checker 和产品验收门；任何一项缺失都不能宣布整个 Goal 完成。
