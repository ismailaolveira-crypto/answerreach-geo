## 1. 产品要解决什么

这是春秋元泉内部使用的 GEO 观测与优化工作台。它将一个采购问题在选定模型中重复进行联网观测，并把每一条回答、引用来源、品牌/竞品出现情况和批次信息保存为可追溯的观测记录。

用户应能完成一条闭环：

1. 在“模型与渠道”保存并诊断模型官方 API 渠道。
2. 在“决策地图”多选已连接模型、常用或临时问题、每题运行次数。
3. 后台按“模型 × 问题 × 轮次”生成任务并持续写入观测结果。
4. 在决策地图、问题库、竞品对比、信源地图中查看同一批真实数据。
5. 从证据发现内容缺口，进入“优先行动”；内容生成与平台草稿同步仍是待接入能力，不能伪装成已发布。

## 2. 当前代码边界

### 前端

- 技术：Next.js 15，目录：`apps/web`。
- 主入口：`/geo/1`。
- 主要页面：
  - 决策地图：`/geo/[workspaceId]`
  - 信源地图：`/geo/[workspaceId]/sources`
  - 竞品对比：`/geo/[workspaceId]/competitors`
  - 问题库：`/geo/[workspaceId]/questions`
  - 历史批次：`/geo/[workspaceId]/batches`
  - 优先行动：`/geo/[workspaceId]/actions`
  - 模型与渠道：`/admin/providers`
- 新版优先行动的 UI 主组件：
  `apps/web/app/(app)/geo/[workspaceId]/actions/priority-actions-workbench.tsx`。

### 后端

- 技术：FastAPI + SQLAlchemy，目录：`apps/api`。
- GEO v1 路由：`apps/api/app/v1/routes.py`；前端适配：
  `apps/web/src/lib/cleanroom-v1-api.ts`。
- API 前缀：`/api/v1`。
- 统一记录主线：工作区 → 问题 → 观测批次 → 单条观测/证据 → 竞品与信源分析 → 优先行动。
- 本地开发默认数据库：`apps/api/geo_platform.db`，不应上传或随压缩包分发。

## 3. 本地启动（必须同一副本）

务必在本副本根目录启动前后端；不要将某个副本的前端连接到另一个副本的 8000 后端。

```bash
pnpm dev:web
pnpm dev:api
```

服务地址：

- Web：`http://localhost:3000`
- API：`http://127.0.0.1:8000`

启动后检查两个进程的当前目录是否都是本副本：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
lsof -a -p <PID> -d cwd -Fn
```

本次已修复过一次“3000 来自新副本、8000 来自旧副本”的问题；它会表现为页面 `Not Found`，调用栈指向 `cleanroom-v1-api.ts`。这不是 UI 问题，而是后端路由版本错配。

## 4. 已具备的能力

- 统一的模型/问题/轮次任务矩阵与批次状态显示。
- 保存原始回答、来源 URL、原始工作件等可审计数据。
- 官方 API 采集适配器及联网结果入库门槛：没有搜索事件、来源 URL 和最终回答时，不应计入决策指标。
- 问题库、单问题分析、竞品排名/证据页、信源统计和批次历史页。
- 基于已入库证据的优先行动机会推导；现阶段行动状态可保存，内容生成、人工审核、写入第三方草稿、人工发布与复测需要逐项接入真实后端能力。

## 5. 当前必须谨慎处理的事项

1. **不要把连接测试当成真实联网观测。** 每个平台必须实际返回搜索证据、来源与回答，才可写入指标。
2. **不要将 API Key、`.env`、SQLite 数据库或历史备份上传。** 本仓库 `.gitignore` 已排除这些文件，但提交前仍需扫描。
3. **不要同时启动多个 r3/旧副本。** 3000 和 8000 只能各有一个对应当前工作副本的进程。
4. **不要把等待队列当作完成。** 批次页应该以任务终态和每条观测实际入库为准。
5. **优先行动页面当前先对齐前端体验。** 对内容生成、平台草稿同步、人工发布、复测的后端接口必须有真实状态机后再标记完成。

## 6. 建议的新对话接手顺序

1. 先确认当前 Git 分支、服务进程 cwd 与本文件路径一致。
2. 运行 `pnpm run check:web`，再启动 Web 与 API。
3. 用一个问题 × 一个模型 × 一轮验证：任务创建 → API 返回 → 单条观测入库 → 证据页展示。
4. 再扩展到多模型、多问题、多轮次；逐个核对每个任务矩阵单元的状态。
5. 最后接优先行动的真实后端：证据缺口 → 内容计划 → 草稿 → 人工审核 → 发布助手 → 复测批次。
